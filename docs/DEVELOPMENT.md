# Development guide

How the code is organised, the commands to build and test it, and the conventions to follow when changing it.

## What this is

A self-hosted Casambi lighting-control appliance for a Raspberry Pi: one Node.js (Express) process serves a React UI, a versioned REST API (`/api/v1`), an SSE event stream, and a cron/solar scheduler, and supervises a long-lived Python subprocess that talks Bluetooth via the unofficial, alpha-quality [`casambi-bt`](https://github.com/lkempf/casambi-bt) library. Real hardware is never touched by tests. See `docs/ARCHITECTURE.md` and `docs/API.md` for full design and endpoint reference.

## Commands

```bash
pnpm install
pnpm check                      # tsc --noEmit (test files are excluded from tsconfig)
pnpm test                       # vitest run (server/**/*.test.ts + client/**/*.test.ts)
pnpm vitest run server/store.test.ts          # single file
pnpm vitest run -t "name of test"             # single test by name
pnpm build                      # vite build (client) + esbuild server -> dist/
CASAMBI_MOCK_MODE=true pnpm dev # tsx watch server/_core/index.ts with Vite middleware
./scripts/validate-package.sh   # build + twine check + smoke test the Python companion wheel (what CI runs)
CASAMBI_JWT='…' node scripts/verify-live-bridge.mjs  # hardware smoke test, only on a connected Pi
```

- Node 22+ is required: the store uses the built-in `node:sqlite` (`DatabaseSync`), loaded via `createRequire` and marked `ssr.external` in `vitest.config.ts`.
- `server/casambi/casambi_worker.test.ts` spawns `python3` on the real worker script, so a Python 3.11+ interpreter must be on PATH for the full suite.
- `pnpm build` writes the web app to `dist/`; `validate-package.sh` writes the Python package to `build/python-dist/`.
- CI (`.github/workflows/app.yml`) runs `pnpm check`, `pnpm test`, `pnpm build`, and shellcheck; `python-package.yml` validates the Python companion package.

## Architecture

**Request path:** `server/_core/index.ts` wires everything together: `LocalStore` (SQLite) → `EventHub` (SSE) → `JsonLineCasambiBridge` (Python supervisor) → `CasambiService` → `DurableScheduler`, then mounts `createCasambiApi` from `server/api.ts` at `/api/v1`. The scheduler runs commands through `casambi.control()`, the same validated path the REST API uses.

**Layout:** `server/_core/` holds only the entry point (`index.ts`) and the Vite/static serving (`vite.ts`, development-only Vite import). Of the shadcn components only `button`, `card`, and `sonner` remain under `client/src/components/ui/`; add others with the shadcn CLI (`components.json`) when needed. The application is:
- `server/api.ts`: REST routes. Request schemas live in `server/apiSchemas.ts` (zod), shared with `server/openapi.ts`, which builds the OpenAPI 3.1 document served at `/api/v1/openapi.json`; `server/openapi.test.ts` fails when a route is added without documenting it, or when a route's documented role differs from what it enforces. `classifyError()` maps thrown errors to statuses: "does not exist" → 404; "required", "invalid", "must", "cannot" → 422; SQLite UNIQUE → 409. Keep error messages consistent with that mapping. Use a separate PATCH schema without `.default()`s (zod's `.partial()` keeps defaults).
- `server/events.ts`: the SSE hub. Pass an audience to `publish()` for anything not every user may see (`"admins"`, or `{ ownerUserId }` for per-account data); `connected` carries the web build ID that makes open pages reload after an update.
- `server/diagnostics.ts`: the admin system check. `gatherSystemFacts` reads the Pi without privileges through injectable `Probes` (systemctl, busctl, iw, timedatectl, /sys), each with a timeout and null on failure, so it works inside the systemd sandbox; `evaluateChecks` is pure and turns the facts into checks with advice. Never suggest network changes there unless a cable is connected (see the radio check).
- `server/backup.ts` + `LocalStore.exportDatabase/restoreDatabase`: backups are the SQLite database (`VACUUM INTO`) plus the decrypted Casambi secrets, sealed with an admin passphrase (scrypt + AES-256-GCM, header as AAD), so they restore on a Pi with another `CASAMBI_ENCRYPTION_KEY`. A restore opens the file as a `LocalStore` first (schema upgrade), then copies `BACKUP_TABLES` in one transaction; add new tables to that list.
- `server/store.ts`: the single SQLite repository (users, API keys, encrypted Casambi config, rooms, unit metadata, schedules, away-date sets, audit log). There are no migrations framework or Drizzle here. The schema lives in this file.
- `server/auth.ts`: JWT (`CASAMBI_JWT_SECRET`) and `X-API-Key` auth, with `admin`/`user` roles. JWTs carry the account's `token_version` (raised by a password reset). They also carry the store's `sessionEpoch`, which a restore renews, so no session from before a restore stays valid. Creating the first admin needs the one-time code from `server/setupCode.ts` (file `setup-code` next to the DB; `pnpm dev` logs it). Outside `NODE_ENV=development` the server sends a strict CSP via helmet, so the built client must not rely on inline scripts.
- `server/scheduler.ts` + `server/solar.ts`: five-field cron evaluated each minute with a `lastRunKey` idempotency guard. There are also sunrise/sunset schedules with offsets (suncalc, which needs admin-configured lat/long), per-timer holiday dates, and reusable away-date sets.
- `client/src/lib/localApi.ts`: the typed fetch client and session storage (localStorage). The session JWT never goes in a URL: live events open `/events?ticket=…` with a one-minute ticket from `POST /auth/event-ticket` (`api.eventUrl()`), fetched again for every new stream.

**Python bridge protocol** (`server/casambi/bridge.ts` ↔ `casambi_worker.py`): newline-delimited JSON over stdio. Each command (`discover`, `configure`, `connect`, `disconnect`, `snapshot`, `control`, `ping`) carries a UUID `id` and gets exactly one `{id, ok, result|error}` response. Unsolicited `{event: …}` envelopes carry state, switch, and connection changes. Node serializes commands (one at a time, which keeps BLE writes ordered), puts a timeout on each one, and restarts the child with capped exponential backoff. `CasambiService.runControl` sends absolute-value operations through `executeLatest`, which replaces an unsent value only when it's the last command in the queue, so newer slider values supersede older ones without reordering anything. Shared types and `controlRequestSchema` are in `server/casambi/types.ts`. `CasambiService` overlays local custom names and rooms on bridge snapshots, because upstream has no room model. A `control` payload with `"reply": "ack"` gets `{ok: true}` instead of a full snapshot; series of commands (fade passes, rooms and scenes lamp by lamp) use it and read one snapshot at the end, because a snapshot per command makes a series cost grow with the square of the lamps. `server/casambi/commandPlan.ts` turns a set of lamps into the fewest network/group/unit commands; use it for anything that sets many lamps. Control replies also carry `bleMs`, the time spent in the casambi-bt call, summarized in `/admin/worker`. After each control command the worker checks `casa.connected`, because casambi-bt swallows a write that fails with "Not connected"; after a connect it reports units casambi-bt skipped because their fixture type failed to load (it caches that failure for 7 days). Both read casambi-bt internals or state without I/O; keep such checks free of awaits so they add no latency. The experimental `fastWrites` setting (write-without-response) replaces `write_gatt_char` on casambi-bt's current BleakClient after the handshake (`set_fast_writes`), reapplied before each command because casambi-bt creates a new client when it reconnects; the worker `options` command switches it without reconnecting. A connect writes one "Connected in … s: …" (or "Connect failed after … s: …") diagnostic built from casambi-bt's INFO and bleak_retry_connector's DEBUG log messages (`CapturedConnectLogs`), captured in memory only while connecting; casambi-bt hides bleak_retry_connector's reason for a failed Bluetooth connection in the `__cause__` of a blank `NetworkNotFoundError`, which the worker reports.

**Mock mode:** `bridge.ts` passes `--mock` to the worker only when `CASAMBI_MOCK_MODE=true` is set explicitly; `NODE_ENV` never enables it. The app is only ever deployed to a real Pi (there is no test/acceptance environment), so a missing flag must mean real Bluetooth. Tests don't need the flag: they inject a fake bridge or `createChild`.

**Scenes:** besides scenes stored in the Casambi network (`targetType: "scene"`), users save scenes on the Pi: the captured level and colour temperature of each lamp in a group, room, or the whole network (`light_scenes` table, `/local-scenes` routes). `CasambiService.control` handles `targetType: "local_scene"` itself (it never reaches the worker), so timers and switch rules can activate saved scenes, with an optional fade. Lamps are units with a controllable capability (`isLampUnit` / client `isLamp`); switches and sensors are excluded from lamp lists and target pickers.

**Units/conventions:**
- The UI shows brightness as 0–100%, while Casambi commands use 0–255. Convert with `client/src/lib/brightness.ts`.
- The friendly timer form (`friendlySchedule.ts`) is translated into cron for the backend. The REST API still accepts raw `cronExpression`.
- Casambi secrets are encrypted at rest with `CASAMBI_ENCRYPTION_KEY`. Changing that key makes the stored secrets unreadable.
- The path alias `@/` → `client/src`.

## Deployment notes

- `deploy/install.sh` is the single install *and* update command for a fresh Raspberry Pi OS 64-bit (it must stay executable in git, mode 100755). It installs apt packages and Node.js 22 from the NodeSource apt repository (configured directly, never `curl | bash`; the signing key must match `NODESOURCE_KEY_FINGERPRINT`), hands a `sudo git clone`d checkout to the invoking user, builds `.venv`/`node_modules`/`dist/` as the checkout owner (never root; root-owned build files cause `EACCES` on updates), creates the `casambi` service account (in `bluetooth`) and `/var/lib/casambi-bt-webui/` (`CASAMBI_DB_PATH`, `CASAMBI_CACHE_PATH`), writes `/etc/casambi-bt-webui.env` with generated secrets only on the first run (later runs keep it and append new template keys), renders the unit for the actual paths/node binary, restarts the service, and waits for `/api/v1/health`. The code in `/opt/casambi-bt-webui` is read-only to the service. Env template: `deploy/environment.template`.
- Updates from the app: the service only creates `/var/lib/casambi-bt-webui/update/{check,apply}-request` (`server/updates.ts`); the `casambi-bt-webui-update-{check,apply}.path` units start `casambi-bt-webui-update@{check,apply}.service`, which runs `deploy/update.sh` as root (also daily via the timer). It fetches the upstream branch, fast-forwards as the checkout owner, runs `install.sh`, and on failure resets to the previous commit and installs that again. It writes `status.json` to the root-owned `/var/lib/casambi-bt-webui-updater/` (readable, not writable, by the service) and never reads anything the service writes. It runs from a copy of itself, because a merge rewrites the file. `install.sh` installs these units and directories.
- `deploy/install.sh` installs the Python bridge from `requirements.lock` (`--require-hashes`, every transitive package pinned). After changing `requirements.txt`, regenerate the lock with the `uv pip compile` command in its header.
- The systemd unit is sandboxed (`ProtectSystem=strict`, no capabilities, only `AF_UNIX`/`AF_INET*`/`AF_NETLINK` sockets). Bluetooth works because BlueZ is reached over D-Bus; a feature that needs raw HCI sockets, device nodes, or writes outside `/var/lib/casambi-bt-webui` needs the unit changed too.
- The unit and env templates are duplicated under `src/casambi_bt_webui/templates/` for the Python companion package (`casambi-bt-webui doctor|systemd-template|write-templates`). Keep both copies identical; `scripts/validate-package.sh` (CI) fails on any drift.
- Upstream quirk: the bridge keeps the `BLEDevice` from its immediate discovery scan, because otherwise upstream re-looks it up in the BlueZ cache, where the entry may have expired.
