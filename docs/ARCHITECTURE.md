# Casambi BT WebUI Architecture

## Deployment model

The production target is a **single Raspberry Pi**. The Node.js process serves the React application, the JWT-authenticated REST API, the Server-Sent Events stream, and the scheduler. It starts one long-lived Python subprocess that imports `casambi-bt`; this subprocess owns Bluetooth interaction and communicates with Node.js over newline-delimited JSON on standard input/output. SQLite stores local users, API keys, Casambi connection settings, room metadata, schedules, and an audit log. Credentials are encrypted at rest using an application secret supplied through the service environment.

| Layer | Responsibility | Availability boundary |
| --- | --- | --- |
| React client | Cyberpunk Admin Panel and User Dashboard; receives live state events. | Browser session |
| Node.js application | Authentication, authorization, REST, validation, audit, scheduling, SSE fan-out, and Python supervision. | systemd service |
| Python bridge | Discovery, connection ownership, Casambi unit/group/scene operations, and state event serialization. | Child process |
| SQLite | Durable local configuration and operational metadata. | Raspberry Pi filesystem |
| Casambi BLE network | Physical lighting controls and asynchronous device status events. | Bluetooth adapter |

## Supported bridge contract

The upstream `casambi-bt` project describes itself as a Bluetooth-based, alpha-quality interface that currently exposes **units, groups, scenes, unit capabilities, switch events, and unit state-change callbacks**. It does not model rooms as a first-class entity. The WebUI therefore stores custom room assignments locally and makes its feature visibility capability-aware. Every unit response includes the supported controls discovered from the upstream `UnitType` model, rather than promising a control that a fixture does not support. [1]

The bridge accepts `discover`, `configure`, `connect`, `disconnect`, `snapshot`, `control`, and `ping` commands. `control` supports the upstream operations `on`, `off`, `set_level`, `set_temperature`, `set_color`, `set_white`, `set_vertical`, `set_slider`, `set_xy`, and `activate_scene`. Each request has a UUID command identifier. The Python process writes a single response for each command and separately emits `event` envelopes for state updates, switch actions, and connection changes.

## Reliability strategy

Node serializes bridge commands to preserve Bluetooth request ordering, applies bounded command timeouts, tracks pending commands by ID, and broadcasts structured failure information without losing the service process. If the child process exits unexpectedly, the supervisor rejects pending requests, publishes an unavailable status, and restarts it with capped exponential backoff. Because the worker handles one command at a time, a command that outlives its timeout means the worker is stuck, and every later command would time out while the process stays alive; the supervisor therefore restarts a worker that misses a timeout (SIGTERM so it can release the BLE link, SIGKILL after 8 s), after which the normal restart and automatic reconnect take over. The Python worker reports a normalized `{ code, message }` error for every failed command (including malformed input) rather than leaking tracebacks over the protocol; before a (re)connect it bounds closing the previous connection (8 s) and the Bluetooth scan (20 s), so a BlueZ call that never returns cannot block it. When the startup connect fails, or an established connection drops or the worker restarts, the Node service retries the connect automatically after 15 s, 30 s, 60 s, and so on, capped at 5 minutes, until it succeeds. A manual Connect or Disconnect cancels pending retries, a manual Disconnect is never undone automatically, and a rejected network password stops the retries until an administrator intervenes. Read endpoints such as `GET /network` serve the last known state, so they never wait behind a connect in the serialized bridge queue. On SIGTERM, SIGINT, or when Node closes its stdin, the Python worker disconnects the upstream connection (bounded to 5 s) before exiting: BlueZ owns a BLE link rather than the process that opened it, so an unclean exit would leave the Pi holding the link and make the next connect attempts fail.

The bridge has an explicit `CASAMBI_MOCK_MODE` development mode. It uses deterministic in-memory units only when this flag is enabled; production mode never substitutes invented devices. This allows interface development without a Bluetooth controller (`CASAMBI_MOCK_MODE=true pnpm dev`), while preserving a clear boundary between simulated and live data. Automated tests do not use it; they inject a fake bridge or worker process.

## HomeKit bridge

`server/homekit/` publishes the Pi as a HomeKit bridge with [HAP-NodeJS](https://github.com/homebridge/HAP-NodeJS), the library Homebridge is built on, inside the Node.js service instead of as a separate Homebridge process. An administrator turns it on in Admin → HOMEKIT. The settings (on/off, name, port; default 51827, next to Homebridge's 51826) and the pairing identity (HAP device id, setup code, setup id) live in the `settings` table; HAP's own keys and the list of paired controllers live in `homekit/` next to the database. A backup carries those keys and pairings (read and written through HAP-NodeJS's own storage, which keeps them in memory), so a restore, also on another Pi, republishes the same bridge and Apple Home keeps it. If the folder has no keys for the stored device id (a backup from before HomeKit support, or a deleted folder), the bridge takes a new device id instead of answering controllers it cannot authenticate. The system check reports the bridge: failed (with advice for a busy port), not announced on the network (avahi advice), ready to pair, or paired; it never includes the setup code. On Linux the bridge is announced through the existing avahi-daemon over D-Bus (HAP-NodeJS falls back to bonjour-hap when avahi is not reachable); elsewhere through ciao; `CASAMBI_HOMEKIT_ADVERTISER` overrides this. HAP-NodeJS has no error handler on its listening socket, so the port is probed first and a busy port is reported as a failed state rather than crashing the service. Start, stop, settings changes, and pairing resets run one at a time; pairings, unpairings, resets, and failures are audited, and the setup code never is. On shutdown the bridge withdraws its announcement (bounded to 2 s).

The protocol-neutral part lives in `server/lighting/`: which lamps, groups, rooms, scenes, and wall switches exist and their state (`model.ts`), colour conversions (`colour.ts`), the list each platform shows with its hidden keys and learned buttons (`registry.ts`, settings under `homekit.*`), and write batching (`writes.ts`); `server/homekit/lights.ts` builds the HAP accessories on top. Every lamp, every Casambi group, and every local room is a HomeKit Lightbulb, except duplicates that Apple Home would show twice: a group or room with a single lamp, and a room with exactly the lamps of a Casambi group, as the setup wizard creates them (the group is kept, since it is switched with one Bluetooth command). Each light (`server/homekit/lights.ts`) has On, and Brightness when one of its lamps dims; switches and sensors are not shown. Accessory ids derive from the unit's Casambi UUID, the network and group id, or the room id, so they stay the same across restarts. Reads answer from `CasambiService.cachedSnapshot()` and never wait for Bluetooth; while the network is disconnected, or none of a light's lamps is reachable, they answer "No Response". `CasambiService.onStateChange` pushes changed values. Writes are collected for 75 ms, merged per light (On and Brightness arrive separately; brightness 0 means off), and planned with `planTargets`, so switching a Home room or scene lamp by lamp becomes one group or network command; On uses Casambi's own `on`, which restores each lamp's last level. They go through `CasambiService.control` as actor `homekit`, so they are audited and reach the web UI live. The list of lights is kept in the `settings` table: after a restart, or while Bluetooth is still connecting, Apple Home finds every light instead of deleting it with its room and automations. A deleted room, or one that becomes a duplicate, disappears at once; a lamp or group that is missing from a connected network disappears after 10 minutes. HomeKit allows 149 accessories per bridge; lights beyond that are counted in the Admin panel. A lamp with a temperature control also gets ColorTemperature (in mired, limited to the lamp's kelvin range and HomeKit's 140–500), and one with RGB or XY colour gets Hue and Saturation; a group or room gets what any of its lamps supports. Each lamp is sent a colour in the form it takes: kelvin to white lamps, RGB to RGB lamps, CIE xy to XY lamps, and the matching white to colour-only lamps when a colour temperature is picked; lamps that cannot show a colour are left alone. Colours go out before power, so a lamp switched on in a new colour does not flash its old one. The worker reports which colour source (temperature, rgb, or xy) a unit shows, so a lamp with both is reported in the right mode; white light is reported with the hue and saturation of its colour temperature. Casambi scenes and scenes saved on the Pi are HomeKit switches: switching one on activates the scene through `CasambiService.control` (actor `homekit`), and the switch reports on for a second and then turns itself off, as Homebridge plugins do. A deleted saved scene disappears at once; a Casambi scene missing from a connected network after 10 minutes. An administrator chooses in Admin → HomeKit which lamps, groups, rooms, and scenes HomeKit shows; the hidden keys are kept in the `settings` table (`homekit.hidden`), hidden accessories are removed from Apple Home at once, and shown ones come back with the same ids. A Casambi wall switch is a HomeKit remote (category programmable switch) with a stateless programmable switch per button, numbered in order: a tap is a single press and a hold a long press (the release after a hold, and raw activity without a trigger, are ignored), so Home automations can react to them; switch rules on the Pi keep working alongside. Casambi does not report how many buttons a switch has, so the bridge learns each button the first time it is pressed while connected (audited as `homekit.button_learned`) and keeps them in the `settings` table (`homekit.buttons`, by the unit's Casambi UUID); the switch then appears in HomeKit, or gets the new button. Background and decisions are in [`HOMEKIT_PLAN.md`](HOMEKIT_PLAN.md).

## Authorization model

Local accounts have exactly the requested role labels: **admin** and **user**. A password login produces a short-lived signed JWT. The REST API accepts that token in an `Authorization: Bearer` header. API keys are generated once, retained only as SHA-256 digests, scoped to `admin` or `user`, independently revocable, and authenticated through an `X-API-Key` header. The role is re-read from the database on every request, so a role change takes effect immediately, and each token carries the account's token version, which a password reset raises, so a reset signs the account out everywhere. Creating the first admin requires a one-time setup code (`server/setupCode.ts`), written next to the database and printed by the installer, so nobody else on the network can claim a fresh install. Sign-ins are limited to 10 failed attempts per 5 minutes per address, failed attempts are audited, and passwords are hashed off the event loop. Outside development the server sends a strict Content-Security-Policy (`script-src 'self'`, `frame-ancestors 'none'`) via helmet, and the Python worker receives only an allowlisted environment, never the JWT secret or encryption key. Browsers open the SSE stream with a one-minute event ticket (`POST /auth/event-ticket`) as the `ticket` query parameter, because `EventSource` cannot set headers; the session JWT is never put in a URL. An API key is not an account: admin keys file new timers under the first admin, and user keys cannot own timers. `X-Forwarded-For` is trusted only with `CASAMBI_TRUST_PROXY=true` (behind a reverse proxy), so clients cannot evade the rate limit.

| Principal | Allowed actions |
| --- | --- |
| `admin` | Casambi configuration, discovery, connection control, metadata and room management, users, API keys, all schedules, and all lighting control. |
| `user` | Read live network data, control lamps/groups/rooms/scenes, and create or manage permitted timers. |
| API key | Operations permitted by its stored `admin` or `user` scope. |

## Scheduling model

On the Raspberry Pi, the service owns a durable SQLite-backed scheduler. It evaluates validated five-field cron expressions in the timer's IANA time zone with an idempotency guard (`last_run_key`) so a rule cannot execute twice in the same minute. Sunrise and sunset timers (with an offset of up to ±180 minutes) are computed locally from the administrator-configured location and re-armed after each run. Per-timer away dates and shared away-date sets skip runs on those calendar days. One invalid timer is audited and skipped instead of stopping the others from loading. Startup immediately reloads enabled rules. Each execution uses the same validated control pathway as the REST API and writes an audit event. The implementation intentionally avoids relying on browser timers or external cloud scheduling.

## API and live-event design

REST endpoints are grouped under `/api/v1`. Every endpoint returns JSON errors with a stable `code`, human-readable `message`, and `requestId`; so do unknown paths under `/api/v1` (404) and malformed or oversized JSON bodies (400/413). Errors that are not written for people (TypeErrors, SQLite and system errors) are logged on the server and answered with a generic 500. The server publishes `bridge`, `connection.status`, `unit.state`, `network.snapshot`, `switch`, `switch_rule.executed`, `switch_rule.failed`, `local_scenes.changed`, `schedule.executed`, `schedule.failed`, and `schedule.skipped_holiday` events to `/api/v1/events`. `switch` and `switch_rule.*` go to admins only and `schedule.*` to admins and the timer's owner; everything else goes to every stream. Each account or API key may hold 10 streams (another one closes its oldest), and deleting an account, resetting its password, changing its role, or revoking a key closes its streams. Clients request a current snapshot first, then reconcile real-time events by entity ID and timestamp. Every stream starts with a `connected` event carrying the build ID of the served web app (a hash of the built `index.html`); the client reloads when a reconnect reports a different build, so a page left open across an update does not keep running old code.

The machine-readable endpoint catalog is the OpenAPI 3.1 document served at `/api/v1/openapi.json` (request schemas are generated from the same zod schemas the routes validate with, and a test keeps routes and document in sync); [`docs/API.md`](API.md) has the narrative reference and examples. `GET /health` reports only `status`, `bootstrapRequired`, the number of live event clients, and the build ID.
